# 자금집행 (중국법인 자금현황 모니터링)

각 법인의 보유시재, 차입금, 배당가능금액을 한눈에 보여주고 그 변화 추이를 확인할 수 있도록 만든
웹 도구입니다. 관리부 ERP 통합시스템의 세 번째 데이터 모듈로, 회계관리 → 예산관리 → **자금집행**
→ 실적분석 파이프라인의 일부입니다.

**이 모듈의 목적은 "자금 집행 계획"이 아니라 "자금 이상징후 감지"입니다.** 고정 임계치로 자동
경고하지 않고, 추이 데이터를 보여줘서 사람이 판단하도록 설계했습니다.

회계관리, 예산관리, 접대비 앱과 동일하게 바닐라 HTML/JS/CSS + Supabase + GitHub Pages 구조입니다.
Supabase 프로젝트는 회계관리/예산관리와 **같은 관리부 ERP 전용 프로젝트를 공유**합니다 (접대비는 별도 프로젝트).

## 3가지 핵심 기능
1. **보유시재 현황 + BS·CF 대사**: 기초·기말잔액은 **지점이 제출한 재무상태표(BS)의 현금성자산**,
   순증감은 **현금흐름표의 CF-56**에서 가져옵니다. 회계 항등식 `기초 + 순증감 = 기말`이
   성립하는지 매달 자동으로 대사하고, 차이가 나면 법인·지점 단위로 표시합니다.
   본사(finance/system_admin)가 수기로 확정할 수도 있지만 그 값은 **참고기록일 뿐 계산에
   쓰이지 않습니다**. 최근 6개월 추이를 표로 보여줍니다.
2. **차입금 관리**: 모든 차입금이 본사를 통해 진행되므로 본사 담당자만 등록/수정하며, 지점은 조회만
   합니다. **YJC 포워딩·흥아물류는 캐시풀링(매일 마감 후 은행잔고 본사 자동 송금) 적용 법인**이라
   조회 화면에 "표시 금액은 본사예치금 성격" 안내 배너가 뜹니다.
3. **배당가능금액**: 직전 사업연도말 기준 이익잉여금(미분배이익잉여금 + 당기순이익)입니다.
   기준월 BS가 아직 입력되지 않았으면 그 이후 최초 제출월에서 **역산**하고, 어떻게 구했는지를
   화면에 함께 표시합니다. 세무·외환 절차 전 이론치이며 법정 계산식이 아닙니다.

### 왜 BS와 CF를 연결했나 (2026-09)
회계 항등식 `전월말 현금 + 당월 순증감 = 당월말 현금`은 반드시 성립해야 합니다. 그 전에는
좌변만 계산하고 우변(BS)과 맞춰보지 않아서 **틀려도 아무도 몰랐습니다.** 실제로 세 가지가
깨져 있었습니다.

- **CF 순증감이 "유입 + 유출"이었습니다.** 중국 현금흐름표 양식에서 지급현금(`支付的...现金`)은
  양수로 적습니다 — 부호가 아니라 `减:` 라벨이 차감을 표현하기 때문입니다. 소계가 아닌 CF
  계정을 전부 더하면 유입과 유출이 상계되지 않고 "총 거래량"이 나옵니다. 게다가 기말·기초
  잔액 4줄(`CF-57`~`CF-60`)까지 같이 더해졌고, 정작 정답인 `CF-56`은 소계라서 제외됐습니다.
- **기초잔액이 본사 수기 입력에만 의존했습니다.** 본사가 한 달이라도 저장을 건너뛰면 기초가
  0이 되고, `기말 = 기초 + 순증감`이라 그 이후 모든 달이 연쇄적으로 무너졌습니다.
- **배당가능금액이 전 법인 0이었습니다.** 죽은 계정코드(`BS-R67`)를 참조했는데
  `coalesce(..., 0)`이 NULL을 0으로 바꿔서 조용히 0원으로 표시됐습니다.

지금은 양변을 각각 지점 제출자료에서 뽑아 차이를 보여줍니다. **차이가 0이 아니면 그 자체가
이 모듈이 찾으려던 자금 이상징후입니다.** 한쪽이 아직 미제출이면 0이 아니라 "판정보류"로
표시해, 미제출과 "실제로 0"을 구분합니다.

## 구성
- `docs/` — GitHub Pages로 배포되는 프론트엔드
  - `index.html` — 법인/적용년도월/접근키 입력
  - `view.html` — 읽기 전용: 시재 현황+추이, 차입금 목록, 배당가능금액
  - `admin.html` — [본사용] 시재 확정/수정, 차입금 등록/수정/삭제, **법인·지점별 산출근거 대사표**,
    배당가능금액 근거, 전체 법인 통합현황+엑셀 다운로드(시트 3장)
- `supabase/` — 테이블/함수 정의 (`schema.sql`). **회계관리의 schema.sql이 먼저 적용되어 있어야** 정상 동작합니다.
  - `migration_2026-09_bs_cf_link.sql` — BS·CF 연결 + 배당 역산 (함수만, 테이블/데이터 무변경)
- `tools/bump-cache-version.sh` — 배포 전 캐시 버전 갱신

## 배포 방법
`supabase/README-deploy.md`를 따라 Supabase에 스키마를 적용한 뒤,
`docs/js/config.js`의 `SUPABASE_URL`/`SUPABASE_ANON_KEY`를 채우고 GitHub Pages로 배포하세요.

`docs/` 아래의 js 또는 css를 고쳤다면 **커밋 직전에** 아래를 한 번 실행하세요.

```bash
bash tools/bump-cache-version.sh
```

HTML의 `<script src="js/...?v=">` / `<link href="css/...?v=">` 값을 현재 시각으로 한꺼번에
갈아끼웁니다. GitHub Pages는 HTML과 JS를 모두 `max-age=600`으로 내려주기 때문에, 이 값이
없으면 브라우저가 "새 app-*.js + 옛 common.js"처럼 짝이 안 맞는 조합을 들고 있을 수 있고
그 경우 화면이 통째로 비어 버립니다. 버전을 붙여두면 최악의 경우도 "10분쯤 옛날 화면"에서
끝납니다. (`vendor/`는 1MB가 넘는 외부 라이브러리라 일부러 제외했습니다.)

## 로컬 실행
```
python -m http.server 8092 --directory docs
```

## 주의: 계정코드는 한 곳에만
이 모듈이 참조하는 회계관리 계정코드는 전부 `fund_account_codes()` 함수 안에 모여 있습니다.
회계관리에서 계정과목을 교체하면 **그 함수 하나만** 고쳐서 재실행하면 됩니다.
과거에 코드가 함수 본문 여기저기 흩어져 있다가 `BS-R67` 비활성화를 놓쳐 배당가능금액이
전 법인 0으로 표시된 적이 있습니다. 자세한 내용은 `supabase/README-deploy.md`를 참고하세요.
